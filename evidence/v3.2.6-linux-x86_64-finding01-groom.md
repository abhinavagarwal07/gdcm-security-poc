# Finding 1 on Linux x86-64: observed freed chunk and reliable abort

GDCM v3.2.6 (`9c71b163`), Ubuntu 24.04, gcc 13.3, unsanitized `-O2 -DNDEBUG`,
default PIE, stock glibc, `randomize_va_space=2`.

This result is the counterweight to `f1-exploit`. That case supplies the
victim layout itself through a replaced global `operator new[]`; this harness
does not supply a layout and uses allocation hooks only to record addresses.

Two results, and the second is the one that matters for severity:

1. In all 20 retained trials, the allocation following the 24576-byte buffer was
   a freed 2049-byte GDCM scratch chunk. No live object or vtable was observed.

2. Corrupting that freed chunk's free-list metadata is caught by glibc's own
   heap consistency check, which calls abort(). The result is a deterministic
   crash, reproduced by the plain `finding01` harness with no instrumentation of
   any kind.

Consequence: on the tested glibc build, Finding 1 reliably caused denial of
service. No code-execution path was found. Pixel geometry was not varied to
change allocation sizes, and other allocators or platforms may behave
differently.

## Reproduction commands

```bash
CC=gcc CXX=g++ ./scripts/build-target.sh vulnerable none release
export LD_LIBRARY_PATH="$PWD/_build/vulnerable-none-release-gdcm/bin"
ulimit -c 0

_build/vulnerable-none-release-harness/finding01_groom \
  20 fixtures/finding-01/trigger.dcm 0
```

The five uninstrumented runs used the same build and fixture with
`_build/vulnerable-none-release-harness/finding01`.
